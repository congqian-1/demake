## Context

现有实现把重复批次推送和工单重拉处理成新增批次、优化文件、工单及下游预包装层级记录，导致同一业务对象在数据库中出现多份记录，和实际业务“同一批次/优化文件/工单只有一条”的模型冲突。当前改动同时涉及推送接口、工单重拉接口、批次级重拉接口、定时任务、预包装覆盖保存以及相关唯一索引，属于跨模块行为收敛。

核心约束如下：
- 同一批次号下允许多次推送，但只允许补充新的优化文件或新的工单。
- 同一批次号、同一优化文件、同一工单号再次推送时，不新增记录，只重置工单状态并刷新必要时间字段。
- `repull` 和批次级重拉都只是把状态重置为 `NOT_PULLED`，第三方拉取仍由定时任务统一执行。
- 定时拉取落库统一走覆盖逻辑，避免旧层级数据残留。

## Goals / Non-Goals

**Goals:**
- 恢复批次、优化文件、工单单条业务记录模型，消除重复业务对象。
- 明确定义批次推送的去重键和增量补推行为。
- 将工单重拉与批次重拉统一为状态重置操作，避免接口内部直接调用第三方。
- 保证定时任务对预包装数据的保存具备覆盖能力，并且不污染同工单的历史报工关联。
- 让数据库索引与业务唯一性保持一致：工单号不再全局唯一，但业务去重仍以批次+优化文件+工单组合实现。

**Non-Goals:**
- 不修改第三方接口协议与报文字段结构。
- 不重新设计预包装订单、箱码、包件、板件的层级模型。
- 不改变前端查询接口的返回结构，只修正数据生成与重拉触发规则。

## Decisions

### 1. 批次推送以“批次号 + 优化文件名 + 工单号”作为业务去重键

重复推送时先按批次号定位批次，再按批次ID和优化文件名定位优化文件，最后按优化文件ID和工单号定位工单。命中同一组合时，不创建新记录，而是更新已有工单的预包装状态为 `NOT_PULLED`、清空错误信息与重试计数，并刷新批次/优化文件的更新时间。

选择这个方案，是因为用户明确要求同一批次允许多次补推不同优化文件和工单，因此不能再把 `work_id` 做成全局唯一；同时又不能放开到完全允许重复业务对象，否则会回到上一版错误行为。

备选方案：
- 继续按 `work_id` 全局唯一处理：会错误拦截同工单号在不同批次或不同优化文件下的合法场景。
- 继续新增重复记录：与修正后的业务规则相反。

### 2. `repull` 与批次级重拉只做状态重置，不直接拉取第三方

`/{workId}/repull` 只将目标工单状态重置为 `NOT_PULLED`；新增的批次级接口将该批次下所有工单状态重置为 `NOT_PULLED`。第三方调用仍由定时任务批量执行。

这样处理可以把“触发重拉”和“执行拉取”解耦，避免接口请求时长不可控，也避免接口内部和定时任务形成两套落库路径。

备选方案：
- 接口内同步调用第三方：响应时间长，失败重试逻辑分散，和定时任务并发时更容易冲突。

### 3. 定时任务始终使用覆盖保存

所有待拉取工单一律使用 `savePrePackageDataWithOverwrite`。覆盖逻辑需要按当前工单记录关联的预包装订单、箱码、包件、板件范围执行，而不是仅按 `workId` 粗暴删除，否则会误伤同 `workId` 的其他合法业务记录。

这样可以同时满足：
- 重新拉取时旧层级数据被替换；
- 同 `workId` 在不同业务组合下互不污染；
- 报工仍可通过板件软删除与ID复用策略保留关联。

备选方案：
- 新拉取走新增、重拉走覆盖：会保留两套行为，容易再次分叉。

### 4. 索引策略从“全局唯一”调整为“查询友好 + 服务层去重”

需要移除 `mes_work_order.work_id` 的唯一索引，并补充普通索引。批次与优化文件不应因为名称重复推送而再次生成重复记录，因此其唯一性应体现在服务层按业务组合查询与更新，而不是简单依赖错误的全局新增逻辑。对于箱码、包件、板件等下游预包装层级，是否允许重复由覆盖保存时的删除/重建范围保证，不再依赖误导性的跨业务全局唯一约束。

备选方案：
- 保留现有唯一索引并通过拼接字段规避：会把数据模型复杂度转嫁到编码层，且不符合真实业务主键含义。

## Risks / Trade-offs

- [服务层去重逻辑比单纯唯一索引更复杂] -> 通过明确批次/优化文件/工单三级查询顺序，并补集成测试覆盖重复推送、补推新工单、单工单重拉、批次重拉四类场景降低风险。
- [覆盖保存范围定义错误会误删其他数据] -> 按当前工单记录关联的预包装订单链路精确删除，不按 `workId` 做全表级物理删除。
- [旧库上已有唯一索引会阻塞上线] -> 提供独立迁移脚本，先执行索引调整，再部署代码。
- [批次级全部重置可能把失败工单和已拉取工单一起重置] -> 这是预期行为，接口职责就是触发整批重新拉取。
