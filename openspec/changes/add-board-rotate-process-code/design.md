## Context

当前板件主数据已经承载条码、尺寸、坐标、真实打包包号等字段，并且会在第三方预包装拉取、覆盖保存、层级查询、详情查询和报工后详情回读中被复用。`rotate` 与 `processCode` 属于同一层级的板件属性，如果只在接口层临时拼接，会导致覆盖保存、重拉复用、测试数据和数据库结构再次分叉。

这次改动同时涉及以下链路：
- 第三方预包装数据 DTO → 板件入库转换 → `mes_part`
- `savePrePackageDataWithOverwrite` 覆盖保存与逻辑删除板件复用
- 板件层级查询、包装层级查询、板件详情查询返回 DTO
- 初始化 SQL、增量迁移 SQL、测试建表脚本和集成测试

## Goals / Non-Goals

**Goals:**
- 让板件表完整持久化 `rotate` 与 `processCode` 两个字段。
- 让第三方拉取、覆盖保存、重拉后重建都能稳定写入并刷新这两个字段。
- 让所有返回板件实体的接口统一返回这两个字段，避免前端多接口行为不一致。
- 通过数据库迁移和回归测试保证线上升级与本地测试环境一致。

**Non-Goals:**
- 不修改批次、优化文件、工单、预包装订单、箱码、包件的业务语义。
- 不改变现有接口路径和响应层级结构。
- 不对 `rotate` 做业务推导或换算，只负责按上游值落库并返回。

## Decisions

### 1. `rotate` 与 `processCode` 作为板件原始属性直接落在 `mes_part`

两者都属于单个板件自身属性，不应散落在扩展表、JSON 扩展字段或接口层临时结构中。直接落在 `mes_part` 可以保证第三方拉取、覆盖保存、查询返回和测试数据使用同一份字段定义。

这里采用“按上游原值保存”的策略：
- `rotate` 使用字符串列保存，避免后续第三方传值从 `0/1` 扩展为其他枚举时再次改库。
- `processCode` 使用字符串列保存，直接承载工艺代码。

备选方案：
- 使用数值列保存 `rotate`：对当前需求没有明显收益，且会放大上游字段格式变化的兼容成本。
- 使用 JSON 扩展字段：查询、索引、DTO 映射和测试都更复杂，不符合当前项目已有建模方式。

### 2. 板件覆盖保存时把两个字段纳入“插入 + 复用更新”路径

`savePrePackageDataWithOverwrite` 目前对板件采用“旧记录逻辑删除，命中相同 `partCode` 时复用恢复”的策略。`rotate` 与 `processCode` 必须进入这条更新路径，否则会出现：首次拉取有值、重拉覆盖后值丢失，或者历史逻辑删除板件被恢复时字段未刷新。

因此需要统一做到：
- 新插入板件时写入 `rotate`、`processCode`
- 复用已删除板件时同步刷新 `rotate`、`processCode`
- 查询时只返回 `is_deleted = 0` 的有效板件记录

备选方案：
- 仅首次插入写入：会在覆盖刷新后出现脏数据。
- 覆盖时直接忽略旧板件复用：会破坏现有报工历史保留策略。

### 3. 所有“返回板件实体”的接口统一补齐字段

项目里板件信息并不只出现在一个 DTO：批次层级、包装层级、板件详情、报工后详情回读都会返回板件实体。为避免前端同一字段在不同接口中表现不一致，设计上要求所有板件 DTO、summary、hierarchy 节点统一增加 `rotate` 与 `processCode`。

备选方案：
- 只改详情接口：前端仍需混合调用多个接口补字段，不符合“修改所有涉及到的接口”的要求。
- 只在数据库落库不在接口返回：业务价值不成立。

## Risks / Trade-offs

- [第三方字段可能为空或缺失] → 字段采用可空列，缺失时按 `null` 落库并返回，不阻断整体拉取。
- [DTO 改动面较广，容易漏改某个板件返回对象] → 以“所有返回板件实体的 DTO”做一次性排查，并用集成测试覆盖三个核心查询接口。
- [覆盖保存复用逻辑漏刷新字段] → 在板件复用更新路径补显式赋值，并通过“首次拉取 + 重拉覆盖”测试校验。
- [线上库缺列导致部署失败] → 提供独立增量迁移 SQL，要求上线前先执行迁移再发布 jar。

## Migration Plan

1. 新增 `mes_part.rotate`、`mes_part.process_code` 两个可空字段。
2. 同步更新初始化 SQL 和测试建表脚本。
3. 发布代码后，新拉取和重拉覆盖的数据会自动补齐这两个字段；存量老数据若第三方不重新下发，则保持为空。
4. 若需要回滚，可先回滚应用，再保留新增列不删除，避免历史数据丢失。
